# Discover

Use when a process owner brings a recurring pain, not necessarily a request for software.
Ask for one real episode, the present workaround, actors, inputs/outputs, frequency,
exceptions and what improvement would mean. Use permitted, minimized examples;
never require client/therapy/student data in public artifacts. Distinguish owner
knowledge, observations and your hypotheses. Being a manager is not data-export authority.

Trace the current process before suggesting AI. Include time spent preparing data,
checking output, fixing errors and coordinating colleagues. Identify a reversible
initial scope and a manual fallback. Ask only questions that can change the decision;
do not turn discovery into a questionnaire about databases, agents or CI.

Capture one lightweight outcome hypothesis before implementation: current state X ->
intended change Y -> observable signal Z -> condition/time to reconsider. Use a
qualitative observable signal when a numeric baseline is unavailable; record unknowns
instead of inventing targets or deadlines. This is a decision aid, not a mandatory
new document or a promise that the change will work.

Deliver a short problem statement, one observable baseline or explicit unknown,
material rules/exceptions, owner/permission boundaries and next decision. The owner
confirms business meaning, not unfamiliar technical architecture. If the owner asked
only to discuss or plan, do not install skills, create files or change external tools.
Evidence: the actual example/observation and unresolved assumptions, not a synthetic
success story. Continue to Decide when enough is known; no mandatory new document.
