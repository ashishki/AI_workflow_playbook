# Engineering Addons: Codex и Claude Code

Четыре необязательных дополнения для **инженерной работы автора**, не новая
платформа и не обновление Product/Desktop. Статус: подготовлены к проверке.
Исходники общие; формат подключения генерируется для выбранной среды.

| Skill | Когда использовать |
|---|---|
| `playbook-change-intelligence` | Понять последствия PR/коммитов и важные риски перед решением |
| `playbook-decision-clarification` | Уточнить только правила и решения, мешающие следующему шагу |
| `playbook-browser-check` | Проверить настоящий UI доступным браузером; agent-browser — один вариант |
| `playbook-heavy-checks` | Ограничить конкурирующие тяжёлые проверки на VPS через существующий heavy |

Нет обязательного допроса, команды субагентов, второго TDD-процесса или требования
переписать архитектуру. Проверка качества тестов и полезности рефакторинга включена
в уточнение решения, а действующие review gates проекта остаются обязательными.

## Подключение к выбранному проекту

Python 3.11+ требуется **для упаковки/копирования**, не для чтения навыков агентом.
Из закреплённой версии Playbook сначала проверьте исходники и доступность инструментов:

```bash
python engineering/addons/bundle.py check
python engineering/addons/bundle.py doctor
```

`doctor` проверяет только наличие команд в PATH. Он не запускает процессы, не читает
аккаунты и не устанавливает зависимости. Авторизация и фактический запуск неизвестны.

До переноса в другой Governed-проект примените его действующий
[external-skill security policy](../../docs/external_skill_security_policy.md).
Для каждого выбранного skill подготовьте отдельный trust record, закрепите точный
commit и хеш **готового host-specific каталога**, оцените capabilities и выполните
требуемые scan/review и решение владельца. При недоступном SkillSpector запишите
альтернативные проверки и обоснование в соответствии с политикой; неподтверждённые
условия остаются блокером. Подготовка, `check` и `verify` не дают install approval.

Сначала соберите пакет во временную новую папку и проверьте каждый выбранный
каталог до установки. Например, для Codex и одного skill:

```bash
python engineering/addons/bundle.py build --host codex --output /tmp/addons-candidate \
  --skill playbook-change-intelligence
python tools/skill_security_gate.py --root /path/to/project \
  --skill playbook-change-intelligence=/tmp/addons-candidate/.agents/skills/playbook-change-intelligence
```

Для Claude используйте `--host claude` и `.claude/skills/...`; повторите gate для
каждого выбранного skill, с записью целевого проекта. Текущий discovery gate не
ищет `.agents/skills`: явно задавайте `--skill`, в том числе для установленной
Codex-копии. Нулевой результат при отсутствии найденных skills не проверяет пакет.
Для downstream CI нужны две разные проверки. Явный `--skill .agents/skills/<name>`
для каждого установленного Codex skill включает его в security gate; один
`--discover-agent-skills` его не находит. Сам gate не сверяет байты каталога с
записанным в trust record хешем. Поэтому дополнительно запускайте `bundle.py verify`
из **проверенной и закреплённой** версии исходного Playbook для того же host и
точного списка skills; она сравнит каждый файл и отвергнет лишние. Например:

```bash
python /path/to/pinned/AI_workflow_playbook/engineering/addons/bundle.py verify \
  --host codex --project /path/to/project --skill playbook-change-intelligence
```

Проверяйте, что закреплённый commit и собранный из него host-specific каталог
совпадают с одобренными в trust record: `verify` не читает запись и не заменяет
её approval. При изменении версии повторите оценку. В проектах с собственным
процессом применяются их соответствующие правила.

Сначала план без изменений, затем та же команда с `--apply`:

```bash
python engineering/addons/bundle.py install --host codex --project /path/to/project --skill playbook-change-intelligence
python engineering/addons/bundle.py install --host codex --project /path/to/project --skill playbook-change-intelligence --apply
python engineering/addons/bundle.py verify --host codex --project /path/to/project --skill playbook-change-intelligence
```

Для Claude Code замените `codex` на `claude`. Для нескольких дополнений повторите
`--skill` в build/install/verify и выполните отдельный gate для каждого. Без
`--skill` выбираются все четыре: каждый требует проверки до установки. Проект
должен существовать.

| Среда | Куда копируются выбранные skills | Явный вызов |
|---|---|---|
| Codex | `.agents/skills/<name>/` | `$playbook-change-intelligence` |
| Claude Code | `.claude/skills/<name>/` | `/playbook-change-intelligence` |

После вызова опишите задачу обычными словами. Например: «Разбери base..head:
что изменилось в поведении, что проверено и где мне нужно решение. Код не меняй».
Для начала сессии проверьте, что среда обнаружила нужный skill, а не одноимённый
глобальный/plugin-вариант. Если не обнаружила, перечитайте актуальную документацию
среды и при необходимости перезапустите её. Не выдавайте наличие файлов за discovery.

Обе поставки требуют явного вызова: Codex получает `agents/openai.yaml` с
`allow_implicit_invocation: false`, Claude — `disable-model-invocation: true`.
Это настройки выбора навыка, не sandbox и не дополнительные полномочия.
Общее тело инструкции побайтно одинаково. Claude-specific hooks, Skill/Task tool,
динамическое исполнение команд и разрешения инструментам в исходниках не нужны.

Можно установить обе поставки в один проект, если используете обе среды. Но внутри
каждой среды не дублируйте те же skills через глобальную установку/plugin. Установщик
не читает домашние конфиги и не может гарантированно обнаружить такие дубликаты.

## Архив/передача без подключения проекта

`build` создаёт новую папку с готовым layout и `BUNDLE.json`; существующая папка
не перезаписывается. Родительская папка должна существовать:

```bash
python engineering/addons/bundle.py build --host codex --output /tmp/playbook-codex-addons
python engineering/addons/bundle.py build --host claude --output /tmp/playbook-claude-addons
```

Для подключения предпочтительна команда `install`, а не слияние папок вслепую.
Manifest фиксирует хеши файлов; их совпадение не доказывает пользу или безопасность.

## Обновление, прерывание и удаление

Подключение create-only: существующий каталог любого выбранного skill останавливает
всю предварительную проверку, даже если его содержимое совпадает. Нет `--force`,
автообновлений, изменения AGENTS.md/CLAUDE.md, моделей, credentials или global config.
Сначала сохраните прежнюю версию/свои правки. Обновление — отдельное согласованное
действие: убрать только известные каталоги этих дополнений, затем подключить новую
закреплённую версию и проверить. Для отката восстановите сохранённые каталоги.

При прерывании копирования могут остаться частичные каталоги. Это не атомарная
транзакция: `verify` должен остановиться, а повторная установка не затирает остатки.
Не запускайте параллельные установку и редактирование. Сохраните неизвестные файлы,
удалите только подтверждённые остатки подключения и повторите. Симлинки/junctions
в управляемых путях отвергаются; средство не является защитой от враждебного процесса
с теми же правами ОС.

Для отключения удаляются только выбранные `playbook-*` каталоги из соответствующего
skills-пути после проверки своих изменений. Другие skills/приложения не удаляются.
Установка heavy/agent-browser и их обновление — отдельные решения, не побочный эффект.

## Внешние инструменты

`agent-browser`: сначала используйте уже работающий браузер проекта. Для испытания
CLI закрепите конкретную версию, выполните его разрешённую установку отдельно,
прочитайте `--help` и доступный `skills get core`. Не запускайте auto-upgrade/npx latest.
Смена браузерного исполнителя не отменяет проверку версии приложения и просмотр PNG.

`heavy`: исходный проект заявляет Linux/macOS. Windows не объявляем поддержанным.
Нужны согласованные pool/directory/slots для всех участников, `--no-skip-ci` и
`--on-timeout fail`. Не передавайте секреты в аргументах/журналах. Это очередь,
а не ограничитель памяти или гарантия остановки оставшихся дочерних процессов.
