# Использовать в настоящей разработке

## Одна рабочая точка входа

Откройте целевой проект и назовите результат. Основная сессия определяет: новый
проект, продолжение или отдельный эксперимент. Не нужно выбирать Native/Governed
вместо работы: действующий контракт определяется по фактам и не ослабляется.
Если правила конфликтуют, показывается конкретное противоречие, а не новая анкета.

Для разработки самого Playbook используйте [локальное окружение](SETUP_RU.md).
Для инвентаризации доступных инструментов в целевом проекте:

```text
python /path/to/AI_workflow_playbook/tools/playbook_environment.py --root /project --audience engineering --json
```

Это чтение наличия инструментов, не запуск проверок. Для repository tests данного
Playbook нужен Harness Lab; другие приложения не обязаны его устанавливать.
Флаг `--playbook-source` применяется только при проверке среды самого Playbook,
не целевого проекта.

## Продолжить текущий проект

Откройте его рабочую ветку. Агент читает действующие AGENTS/контракт и короткое
состояние, сверяет HEAD, изменения и проверки, продолжает первое незавершённое
задание. Не переносите туда новые шаблоны с `--force` и не заменяйте закреплённую
методику последней экспериментальной версией.

> Продолжи этот проект по его действующим правилам и закреплённому Playbook.
> Проверь реальное состояние, найди первое незавершённое задание и доведи его
> через реализацию, проверки и предусмотренное независимое ревью. Сохрани
> прогресс и ограничения. Модель, доступы и master не меняй.

## Начать новый инженерный проект

Сначала проблема, результат, данные, ограничения, команда и проверка результата.
Затем подходящая глубина проектирования. Используйте существующий
[initializer и Feature Workflow](../tools/README.md) из выбранной закреплённой
версии. `oneshot`, compact design и designed slices — глубина задачи; это не
оценка технической грамотности владельца. Не создавайте пустые документы для галочки.

До запуска согласуйте не только mode и Planning Depth, но и способ работы:
кто выбирает задачи, пишет код и исправления, кто независимо проверяет и кто
принимает результат. Уже согласованные ответы используйте без повторной анкеты.
Для Standard/Strict initializer поддерживает `--delivery-profile solo_verified`
(человек управляет задачами; значение по умолчанию) и `independent_review`
(основная сессия управляет задачами, пишет код и исправления; отдельные агенты
проверяют read-only). Модели и reasoning можно явно записать через
`--agent-model`, `--agent-reasoning-effort`, `--review-model`,
`--review-reasoning-effort`. Эти параметры не переключают модель текущей
сессии и не запускают платные вызовы; фактические настройки проверяются при запуске.
Completion authority не делегируется этим флагом и остаётся у человека.

Initializer создаёт scaffold. В T01/T02 проверьте связность `AGENTS.md`,
delivery contract, `docs/REVIEW_POLICY.md`, короткого `docs/CODEX_PROMPT.md` и
реальных проверок проекта. Для Lean-Core сохраняется малый набор и Codex Direct;
`independent_review` требует Standard/Strict. Пройденный verifier подтверждает
заявленные детерминированные проверки, а не готовность продукта или успешное
исполнение агентного цикла. Зафиксируйте commit Playbook, команды, результаты и
непроверенные части. Следующая design-задача начинается с `plan -> select-plan`,
затем `draft`, ревью и действующего согласования.

Для нового Standard/Strict verifier проверяет обязательные operating-файлы и
согласованность выбранного профиля. Старые проекты автоматически не мигрируют:
исправления переносятся отдельной проверяемой правкой с сохранением их контрактов.
Не запускайте initializer с `--force` для обновления действующего проекта.

## Реализация и проверка

Основная сессия пишет код напрямую. Собственные тесты не являются независимым
ревью. Поддержанные review-роли выполняет
`tools/run_codex_role.py`; остальные — действующий
[exec-протокол](../docs/codex_exec_subagent_protocol.md). Reviewer read-only,
не коммитит и не запускает других reviewer. Недоступный запуск остаётся пробелом.
Полная цепочка Deep Review нужна по правилам проекта на значимых границах,
а не автоматически на каждой правке. Исправления перепроверяются; отчёт должен
относиться к актуальным файлам. `validated` исполнения не означает `PASS` кода.

## Связь с Product

Один и тот же runner, проверка UI, eval и сохранение контекста обслуживают обе
зоны. Product предоставляет понятный разговорный маршрут, не заменяет вашу
архитектурную работу и не отнимает расширенные инструменты. Обратная связь от
пользователей также может породить инженерное улучшение.

## Проверить новый подход без обновления рабочих проектов

Создайте отдельную копию/ветку или ограниченный эксперимент по
[протоколу](experiments/README.md). Запишите исходный способ работы, изменяемый
фактор, реальные ограничения, критерий и бюджет. Сначала механический preflight,
потом разрешённый опыт. Сравнивайте и неудачи; не подмешивайте новые версии в
текущие downstream. Успех автора не равен удобству подписчика.

При завершении любого из трёх маршрутов сохраняются реальное состояние,
незавершённые действия, результаты проверок и следующий шаг. Новая сессия
не должна заново запускать initializer или повторять закрытые фазы.
