# Controlled Delegation: что сделали и зачем

Статус на 9 октября 2026 года. Эта записка связывает результаты эксперимента,
решение о применении и подготовку переноса в актуальный master.

## Вопрос эксперимента

Проверяли, помогает ли главному агенту передача независимых частей задачи
ограниченному числу помощников. Главный агент отвечает за итог, проверяет выводы
и вносит изменения; помощники исследуют отдельные направления. Сравнивали обычный
Codex (A), Playbook с одним исполнителем (B) и Playbook с делегированием (C).
Качество результата, время и расход важнее числа запущенных агентов.

## Выполненная работа

Проведены три раунда настоящих модельных запусков: 15 попыток в первом раунде,
12 во втором и 6 в третьем. Использовались изолированные рабочие каталоги,
фиксированные исходники и критерии, реальные журналы и независимые проверки.
Синтетическими были задачи и данные; модельные прогоны не имитировались.

После первых раундов исправили точность денежных расчётов и оценщик результатов.
В третьем раунде проверили связанный проект из 67 файлов: резервирование товара,
состояние заказа и возвраты. Все шесть приложений исправили три причины сбоя
и получили 100/100 по закреплённым проверкам. Независимое полное ревью подтвердило
код и объяснения, обнаружило ошибку классификации; повторная проверка исправлений
и скорректированной интерпретации дала PASS.

Оценщик искал текстовые маркеры в нечитаемых поручениях помощникам. Это породило
четыре необоснованных FAIL. Их первоначальные записи сохранены, а отдельная
интерпретация отмечает BLOCKED: инструкция не проверена, нарушение не доказано.
Реальные команды помощников из STATE A2 найдены в связанных child traces.
Неудачные попытки, STOP_SHIP, preflight и исходные хэши не переписывались.

## Вывод и границы

Польза делегирования на проверенных задачах не показана. В третьем раунде C
был медленнее B в обоих повторах: медианы 354 и 242 секунды, отношение 1.46.
Входных токенов без кеша потрачено в 2.93 раза больше, выходных — в 1.69 раза.
Это токены, а не измеренная денежная стоимость. USD и активное время человека
неизвестны; полная qualification остаётся BLOCKED.

Практическое решение — один агент по умолчанию. Делегирование остаётся
экспериментальным вариантом для задач с независимыми направлениями поиска;
новую пользу нужно доказать на конкретном сценарии. Два повтора одного среднего
синтетического проекта не описывают большие реальные проекты. A также получил
неоднозначную общую инструкцию и фактически использовал помощников; его нельзя
считать чистым одиночным baseline. Основное сравнение — C с B.

## Зачем подготовлен отдельный перенос

Проверка GitHub показала, что серверный master — `f03dde86`, а локальный master
отставал на 17 коммитов. Ветки docs и vNext уже входят в серверный master.
Экспериментальная feature-ветка содержит также десять Delivery/Desktop-коммитов
из незавершённого draft PR #10. Поэтому подготовлен минимальный перенос архива
результатов и этой поясняющей документации от актуального master; рабочий runtime,
Delivery и автоматическое включение делегирования в него не входят.

Для этого восстановлены точные Git-байты актуального master, подготовлена ветка
`docs/controlled-delegation-results-20261009` и проверено её дерево. В архив добавлены
два точных экземпляра ранее проигнорированного Git Python-кеша, на которые уже
ссылались замороженные индексы. Все 676 индексированных SHA256 совпали.
Кеш остаётся историческим свидетельством внутри reports и не используется runtime.

На подготовленном дереве прошли 29 vNext tests, Native tests (24, один skip из-за
root), проверка контрактов, runtime sync и проверка diff. Полный pytest и canonical
validation не названы зелёными: недостающая установка Harness Lab и шесть ссылок
на отсутствующие старые pilot-файлы воспроизведены также на чистом master.
Свидетельства pilot не выдумывались, чужая незавершённая работа не сливалась.

## Состояние публикации и следующий шаг

Владелец разрешил commit, push и перенос результатов. Предыдущая попытка записи
через GitHub была отклонена средой: `approval policy: never`. После нового явного
разрешения повторена публикация: GitHub снова отклонил создание ветки с сообщением
`MCP tool call requires approval, but approval policy is never`. Разрешение владельца
само по себе не меняет этот технический режим. Remote push и merge — NOT RUN;
server master остаётся f03dde86. В подготовленной локальной ветке уже есть коммиты
архива `3d1730f` и поясняющей документации `3835e0e`; исходная экспериментальная
ветка на GitHub остаётся ad55ee4. Итог публикации нужно проверять по remote SHA,
PR и CI; локальный commit не выдаётся за push.

Для завершения: опубликовать подготовленную ветку в среде с разрешённой записью,
перепроверить master и scope diff, выполнить CI и затем merge. Старые ошибки
полного master-verifier требуют отдельного исправления test setup и проверки
ссылок на исторические приватные свидетельства. Они не превращаются в PASS из-за
переноса отчётов и не означают разрешение rollout.
