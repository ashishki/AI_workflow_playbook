# Playbook Native: план до полезного продукта

Пересмотр 2026-09-19. Кандидат preview.6. План заменяет CF-00–CF-09 и не является
процессом, который должен выполнять подписчик. [Модель продукта](CODEX_FRONTEND_SKILLS_MCP_ADOPTION_RU.md),
[протокол автора](../native/DEVELOPMENT_RU.md), [история испытаний](../../reports/native/README.md).

Цель следующей итерации — установить, **за что пользователю стоит подключать
Playbook**, и убрать лишние действия. Красивый старт и работающий ZIP сами по себе
этого не доказывают. Пакет остаётся экспериментальным до соответствующих проверок.

## Что уже есть

| Часть | Подтверждено | Граница подтверждения |
|---|---|---|
| Пакет | Два skills, короткий блок, существующий Role Runner, версионируемый ZIP | Не доказательство улучшения агента |
| Вход | Подготовленная папка в Codex; START теперь необязателен | Самостоятельный новичок ещё не прошёл весь путь |
| Режимы | Три независимых измерения, plan/check boundaries, переключение в чате | Нет полного model-покрытия всех сочетаний |
| Три ОС | Package/runtime fake CLI/Chromium CI Windows/macOS/Linux | Не desktop и настоящее ревью моделью на каждой ОС |
| Lifecycle | Linux CLI install/reinstall/update/remove и fresh-session discovery | Остальные hosts, monorepo и негативные fixtures ещё нужны |
| Реальный результат | Отдельные исправления, новый сайт и независимые browser checks | Небольшие примеры не подтверждают превосходство над plain agent |
| Автоматическое ревью | Механизм включён; отдельный реальный review нашёл дефект | Вложенный CLI заблокирован в текущем eval-host |
| Harness Lab | Шесть задач, внешние проверки, receipts и compare | Новые booking/contacts оценивают инструкции без reviewer |

Конкретные версии, числа, неудачи и ограничения находятся в отчётах. Не меняем
прошлые результаты задним числом. Master и downstream не затрагиваются.

## 1. Проверить полезную разницу

Первый шаг — [зафиксированный plain/current/lean опыт](../../evals/native/VALUE_CHECK_RU.md):
бронирования и экспорт контактов, равные условия, по две попытки, до 12 запусков.
Проверяем сохранность и выполнение задачи внешними оценщиками. Исходные ошибки,
контрольные решения и мутанты проверяют сами оценщики.

Решение принимаем по заранее заданным критериям: результат, границы, честность,
затем затраты. Неполный запуск с правильным кодом остаётся неполным запуском.
Ничья не становится преимуществом Playbook. Сокращение текста не выдаём за
измеренную экономию model tokens. Не выбираем только удачные попытки.

Следующий полный опыт требует среды, где штатно доступны reviewer и, для UI,
браузер. Не меняем разрешения ради зелёного результата. На свежих задачах сравниваем
plain agent с полным пакетом; при необходимости отдельно отключаем один компонент,
чтобы понять его вклад. Учитываем токены reviewer, реальные найденные дефекты,
ложные замечания, исправления, время и ручные подсказки. Новая лаборатория не нужна.

**Условие решения:** оставить полезный механизм, сузить его область, убрать или
записать «недостаточно данных». Автоматический reviewer пока сохраняется по явному
решению автора; его роль в полном продукте проверяется отдельно от skills-only.
Если равный plain решает задачу так же хорошо, следующим шагом служит наблюдаемая
проблема пользователя, а не новый набор универсальных инструкций.

## 2. Проверить первый самостоятельный запуск

Основной путь: распаковать → открыть «Мой проект» в Codex → написать задачу →
открыть результат → продолжить. START проверяем как справку при затруднении.
Не заставляем каждого пользователя выбирать параметры на отдельной странице.

На Windows, macOS и Linux нужно наблюдать настоящий desktop-вход, обнаружение
skills, доступность CLI reviewer, открытие результата и продолжение на следующий
день. Отдельно — свой проект, обновление и удаление. CI пакета этого не заменяет.
[Пилот](../native/PILOT_RU.md) подготовлен; людей не приглашали и пакет не публиковали.

Для 3–5 добровольцев после определения прав считаем подсказки, непонятные термины,
ошибки setup, пропущенные проверки и время до первого используемого результата.
Предварительный продуктовый порог: 4 из 5 проходят без объяснения архитектуры;
при трёх участниках — 3 из 3 и расширение перед общим выпуском. Это не статистика
превосходства. Потеря данных или ложное «проверено» требуют исправления причины.

**Условие решения:** человек сам доходит до результата. Если ему нужен автор на
каждом шаге, упрощаем вход и устраняем конкретную причину. Не отвечаем новой формой
или страницей инструкции на каждую трудность.

## 3. Закрыть наблюдаемые риски подключения и проверки

Необходимые следующие проверки выбираем по изменениям и найденным дефектам:

- Connect/reconnect/update/remove: существующий AGENTS/override, custom skill,
  локальные изменения, monorepo scope, collision и ссылка за пределы проекта.
  Нет дублей или silent overwrite; изменённый skill при удалении сохраняется целиком
  вне discovery. Известная ошибка удаления уже исправлена и перепроверена.
- Frontend: другой обычный stack, сломанный submit при зелёном build, старый
  screenshot, чужой preview на порту, отсутствие browser/image capability.
  Агент проверяет финальное состояние и не приписывает себе внешнюю проверку.
- Non-frontend: никакого обязательного браузера или frontend-процесса; plan-only
  сохраняет файлы, check-only не исправляет исходники. Русские и английские запросы.
- Resume: состояние восстанавливается из проекта и одного существующего note,
  если он нужен. Не вводим параллельные реестры состояния.

[Предыдущая подробная матрица](https://github.com/ashishki/AI_workflow_playbook/blob/f342162688003a0de801b24864a972cc144c4877/docs/research/CODEX_FRONTEND_IMPLEMENTATION_PLAN_RU.md)
сохраняется как справочник, включая решения по CF-00–CF-09. Наличие строки в ней
не означает выполненную проверку. Не строим installer/doctor или browser framework,
пока конкретная повторяемая проблема не оправдывает код вместо инструкции.

## 4. Подготовить выпуск

После проверок: версия архива, контрольная сумма, инструкция на один экран,
известные ограничения, update/remove и способ сообщить проблему. Пользователь
получает только пакет; лаборатория, журналы и исследовательские документы остаются
у автора. Новый ZIP не перезаписывает уже переданную версию.

Нужны права использования фактически распространяемых файлов, результаты desktop
пилота и решение владельца о публикации. До этого не обещаем массовую готовность,
экономию токенов или поддержку Claude Code. Исходный код существует без публичного
релиза; [текущий legal status](../LEGAL_STATUS.md) не меняется этой работой.

## Отдельное сопровождение Governed

Существующие проекты не мигрируют автоматически; их formal review policy сохраняется.
Discovery `.agents/skills` в старом security gate, clipping required context и
формальная identity remote browser records остаются отдельными инженерными задачами.
Две известные frozen-pilot pytest ошибки и старые missing task references не
исправляем переписыванием доказательств. Это отдельный maintenance, не новая
пользовательская стадия Native.

Исполнитель самостоятельно исследует, реализует и проверяет в разрешённой области.
Автор решает права и публикацию; повторное согласование каждого пункта не нужно.
