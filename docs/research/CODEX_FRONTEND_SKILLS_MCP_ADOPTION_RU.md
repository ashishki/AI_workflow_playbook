# Playbook Native: продуктовая модель

Статус: **кандидат на продукт; в ветке есть пробный пакет, публичного релиза нет**.
Пересмотр: 2026-09-19. База исследования: `d070f4e` / исходный core `d570163`.
Область изменений: только AI_workflow_playbook; master и downstream не меняются.

**Предлагаю поставлять небольшой нативный пакет для coding agent:** подключить
репозиторий, поставить обычную задачу, получить реализацию, проверку работающего
результата и понятный итог. Основная аудитория первой версии — индивидуальные
разработчики и небольшие команды, использующие Codex в существующих web-проектах.
Backend-задачи получают короткие общие правила, frontend — дополнительный skill.

Это замена прежней архитектуры proposal, а не расширение CF-00–CF-09.
[Исходный proposal](https://github.com/ashishki/AI_workflow_playbook/blob/d070f4e/docs/research/CODEX_FRONTEND_SKILLS_MCP_ADOPTION_RU.md)
сохранён в Git. Его наблюдения полезны; обязательность ролей, gates и порядка
внедрения не принимается как исходное условие.

Читать дальше: [быстрый старт](../native/QUICKSTART_RU.md),
[пакет](../../plugins/playbook-native/README.md),
[план и критерии выпуска](CODEX_FRONTEND_IMPLEMENTATION_PLAN_RU.md).

## 1. Диагноз текущего Playbook

Сильные стороны: честное разделение claims и evidence, реальные проектные
проверки, защита от ложного PASS, сохранение существующего кода и явные границы
внешних действий. Полезны и специализированные инструменты для команд, которым
нужны формальные review/release records.

Слабое место — цена входа и цена каждой небольшой задачи. Пользователь должен
понимать adoption mode, planning depth, brief, task graph, design approval,
receipts, review roles, continuity docs и readiness. Автоматизация этой системы
не отменяет того, что её приходится устанавливать, понимать и поддерживать.

Локальный замер штатного initializer с минимальными валидными ответами,
без optional packs, 19.09.2026:

| Режим | Создано файлов | Из них tools | Из них schemas | Общий объём |
|---|---:|---:|---:|---:|
| lean-core | 35 | 17 | 8 | 358 657 байт |
| standard | 81 | 19 | 15 | 948 875 байт |
| strict | 82 | 19 | 15 | 952 924 байт |

Это измерение scaffold, а не времени работы пользователя и не токенов модели.
Тем не менее даже минимальный вариант переносит в чужой проект значительную
часть нашего framework. Новый путь должен обходиться без этого переноса.

Другая проблема — конфликт обещаний: README называет ценностью governance,
а желаемый продукт должен позволять агенту самостоятельно доводить задачу.
Нельзя оставить прежние универсальные запреты и поверх назвать workflow простым.
Поэтому Native и Governed имеют явные границы применения.

## 2. Конечная модель и пользовательский путь

**Playbook — тонкий пакет рабочих привычек поверх возможностей агента.**
Он не выбирает модель, не запускает собственный orchestrator и не становится
runtime-зависимостью создаваемых приложений.

| Момент | Что делает пользователь | Что делает агент |
|---|---|---|
| Установка | Устанавливает один пакет из поддерживаемого источника | Host обнаруживает два skill; установка ещё не означает подключение проекта |
| Подключение | «Подключи Playbook к этому репозиторию» | Читает инструкции, находит команды, добавляет короткий блок, сообщает доступность проверки |
| Задача | Описывает желаемый результат; даёт референс при необходимости | Выбирает достаточный план и профильные skills, реализует |
| Проверка | Обычно ничего | Запускает проверки, открывает изменённый экран, проверяет поведение и вид, исправляет |
| Итог | Смотрит результат и существенные ограничения | Показывает diff/preview, выполненные проверки и непроверенное |
| Внешнее действие | Решает о действии, если его ещё не разрешал | Выполняет уже разрешённое; запрашивает только недостающие полномочия |

Для small fix план может существовать только в голове агента и коротком сообщении.
Для задачи на несколько сессий достаточно одного существующего issue/плана с
текущим состоянием, решениями и следующим шагом. Нет обязательных дубликатов
`TASKS`, `CODEX_PROMPT`, journal, evidence index и JSON registry.

**Первый поддерживаемый маршрут:** Codex desktop с доступным браузером.
CLI и IDE используют те же skills, но для UI требуют доступного browser tool.
Переносимость Markdown не является доказательством совместимости всех hosts.
Матрица реально испытанных окружений появится до выпуска; сейчас её нет.

## 3. Минимальная упаковка

Пробный исходный пакет уже находится в `plugins/playbook-native/`:

| Часть | Зачем нужна | Когда читается |
|---|---|---|
| `playbook-setup` | Connect/update/remove, обнаружение проектных команд | При запросе подключения или обслуживания пакета |
| Короткий блок проекта | Самостоятельно доводить задачу, реально проверять и честно сообщать итог | Через нативный `AGENTS.md` / действующий override |
| `playbook-frontend` | Цель экрана → реализация → browser check → исправления | При изменении отображаемого web UI |
| Browser reference внутри skill | Проверять нужный checkout и реальные состояния | При запуске приложения/браузерной проверке |

У plugin нет MCP, hooks, scripts, внешних аккаунтов, собственного CLI и модели.
Основной канал будущего распространения — нативный plugin. Запасной — две
repo-local папки `.agents/skills`, скопированные из того же источника. Не ставить
оба варианта одновременно. Не поддерживать параллельные тексты правил.

В проект попадает один небольшой блок инструкций и, при необходимости,
несколько строк с реальными командами. При repo-local доставке добавляются
папки двух skills. В текущем кандидате block занимает 22 строки; repo-local
payload — четыре файла skills и один файл инструкций, если его ещё не было.
Это размер исходного комплекта, не измерение качества или экономии токенов.
Не копируются `PLAYBOOK.md`, Python tools, schemas и prompts.
Установка не запускает тесты с выдуманными командами и не делает вид, что
неработающий проект готов: она показывает найденные ограничения.

Setup учитывает существующий `AGENTS.override.md`, monorepo scope, collisions,
пользовательские изменения и повторный запуск. Обновление явно запрошено и
сравнивается с установленным содержимым. Удаление затрагивает только свой блок
и свои неизменённые файлы; самостоятельные доработки сохраняются. Это пока
инструкции для агента, а не доказанный детерминированный installer.

## 4. Что автоматическое, а что остаётся человеку

Агент самостоятельно читает релевантный код, выбирает небольшой план, использует
установленные skills, редактирует, запускает команды, проверяет UI, исправляет
обнаруженные проблемы и готовит итог. Не нужно согласовывать каждую роль,
промежуточный файл, повторный тест или локальное исправление.

Человек нужен, когда неопределённость меняет продукт: неизвестна целевая
аудитория, несовместимы требования, меняется бизнес-правило, требуется доступ,
расходы или действие с внешними последствиями. Уже выданное разрешение действует;
новый Playbook не создаёт дополнительного approval поверх host/repo policy.

Для привычной реализации достаточно самопроверки агента и обычного review проекта.
Свежий reviewer полезен при сложной архитектуре, auth/payments/data boundaries,
миграции или явном запросе. Он не обязательная роль для каждого изменения.
Self-check не переименовывается в независимое review. Multi-agent выбирается
только там, где есть отделимая работа и ожидаемая польза; смена поставщика модели
сама по себе не делает review независимым или достоверным.

Ошибки агент исправляет до результата в рамках задачи. После повторения одной
проблемы без новой информации он меняет диагностическую гипотезу или сообщает
конкретный blocker. Нет бесконечного auto-repair, но нет и формального запрета
на третье исправление другой проблемы. Бюджет задаётся пользователем/host,
отдельный cost-contract для разовой задачи не нужен.

## 5. Frontend workflow, которым удобно пользоваться

1. Понять пользовательский сценарий и прочитать существующий экран, компоненты,
   стили и тесты. При локальной правке воспроизвести симптом.
2. Для нового экрана кратко сформулировать визуальное направление, контент и
   существенные состояния. Использовать имеющуюся дизайн-систему; не начинать
   каждую задачу с анкеты или выбора framework.
3. Реализовать изменение. Для бага/поведения добавить полезную регрессию в
   существующий runner. Для CSS-правки не создавать бессмысленный unit test.
4. Запустить релевантные проектные проверки и приложение из текущего worktree.
   Открыть нужный экран, пройти основной сценарий и уместную ошибку/edge case.
5. Проверить внешний вид на затронутых размерах: для responsive UI обычно широкий
   и узкий экран. Открыть свежие screenshots, проверить overflow, иерархию,
   читаемость, focus и клавиатуру; посмотреть доступные console/network данные.
6. Исправить наблюдаемые дефекты, повторить затронутые проверки, предъявить итог.

Визуальную проверку проводит агент с image capability. Человек видит preview и
принимает субъективные/продуктовые решения по необходимости. Отдельная ручная
подпись на каждом screenshot не требуется, если её не требует проект.

Pixel-diff полезен для стабильных повторяемых поверхностей и существующего CI,
но не обязателен для каждого экрана. Новый golden baseline — кандидат на review,
а не доказательство корректности. Не менять threshold/masks ради зелёного теста.
Автоматический a11y-check дополняет проверку клавиатуры и смысла интерфейса.

### Достаточное подтверждение результата

| Утверждение | Минимум для обычной задачи | Когда нужно больше |
|---|---|---|
| «Код проходит проверки» | Реальный command/result, видимый в выводе/CI | Release policy требует долговременный record |
| «Сценарий работает» | Пройденное взаимодействие и наблюдаемый результат | Регрессия критичного пути → сохранённый e2e test |
| «Вид проверен» | Свежий screenshot, который агент действительно открыл | Стабильная visual regression → baseline/current/diff |
| «Проверял именно это изменение» | Запуск из текущего checkout и наблюдаемый признак изменения | Remote preview/release → build/deployment identity |
| «Готово» | Критерии выполнены; ограничения названы | Merge/deploy и риск регулируются проектом |

Один URL/PID/HEAD не доказывает нужную сборку, особенно с dirty tree или HMR.
Для локальной задачи достаточно владеть запуском и увидеть характерное изменение;
при сомнении перезапустить свою сборку. Универсальный hash-ledger для screenshot
не нужен. Remote preview без связи с ревизией остаётся непроверенным.

Если браузера нет, агент выполняет доступные checks и сообщает «UI не проверен»,
указывая минимальный следующий шаг. Отсутствие доступа не означает PASS. Cloud
localhost может не совпадать с localhost проекта; нельзя автоматически публиковать
сервис или создавать публичный tunnel ради проверки.

## 6. Skills и MCP: конкретный выбор

Skills полезны как небольшие предметные инструкции с progressive disclosure.
Разделять один frontend-цикл на design/verify/review skills незачем: увеличиваются
выбор, overlap и вероятность пропустить проверку. Stack-specific рекомендации
подключаются по задаче; весь React/Next.js pack не грузится в статический сайт.

| Потребность | Предпочтение | Когда менять |
|---|---|---|
| Посмотреть/проверить локальный UI | Доступный native browser либо уже установленный browser runner | Нет нужных возможностей/доступа |
| Повторяемая регрессия в CI | Обычный проектный Playwright/e2e test | Другой runner уже принят в проекте |
| CLI без браузера | Один browser CLI; Playwright CLI — стартовый кандидат | Уже есть agent-browser или другой подходящий tool |
| Глубокая диагностика Chrome | Доступные DevTools/CDP; при необходимости DevTools MCP | Реальная проблема требует этих данных |
| Реальный Figma design | Figma integration/MCP при наличии доступа | Для переданного screenshot интеграция может быть лишней |
| Tickets/docs/observability | Existing CLI/API/connector; MCP при удобном native доступе | Снижает конкретную ручную передачу контекста |

Не устанавливать MCP «для зрелости» и не строить отдельный обязательный MCP-пилот
перед выпуском basic pack. Уже подключённый подходящий MCP допустим с первой
задачи. CLI не объявляется универсально быстрее: это проверяемый tradeoff,
зависящий от tool, context и host. MCP разработки не становится библиотекой backend.

Внешнее подключение требует понятного источника, scope, доступа и handling данных.
Repo-local instruction-only skill не нуждается в отдельном многостраничном trust
record для каждой задачи. Executable scripts, новые аккаунты, browser profiles и
remote mutations требуют соразмерной проверки; host permissions остаются в силе.

## 7. Внешние решения: что изменило выбор

Проверены первичные источники 19.09.2026. Это чтение публичных реализаций и
документации; не сравнительное испытание их качества. Community mysetup из
первого исследования остаётся историческим контекстом, не критерием выбора.

| Источник | Наблюдение | Наше решение |

| [GitHub Spec Kit](https://github.com/github/spec-kit) | Явная spec/plan/tasks/implement последовательность | Уместно для сложных specs; не делать проход по командам входом для любого бага |
| [GSD](https://github.com/gsd-build/get-shit-done) | Отдельная система context engineering и spec-driven работы | Не воспроизводить ещё одну систему управления состоянием; качество нами не измерено |
| [Playwright CLI](https://github.com/microsoft/playwright-cli), [Playwright MCP](https://github.com/microsoft/playwright-mcp) | Два browser interface с различными tradeoffs | Переиспользовать доступный; сохранять регрессию как тест, а не новый агентный transcript |
| [agent-browser](https://github.com/vercel-labs/agent-browser) | CLI с interaction/snapshot/screenshot | Совместимый кандидат, не вторая обязательная установка |
| [Chrome DevTools](https://github.com/ChromeDevTools/chrome-devtools-mcp) | Debugging/performance, CLI и MCP; отдельные telemetry settings | Добавлять для диагностики; при подключении проверить настройки данных |
| [Figma MCP](https://developers.figma.com/docs/figma-mcp-server/) | Доступ к контексту реального дизайна | Опционален при наличии макета и доступа |
| [Playwright visual](https://playwright.dev/docs/test-snapshots), [accessibility](https://playwright.dev/docs/accessibility-testing) | Условия capture влияют на diff; автоматическая a11y-проверка неполна | Не путать тест, screenshot и пользовательскую пригодность |

URL на `main` не является закреплённой поставкой. Перед включением внешнего кода
в релиз выбрать конкретную версию и проверить условия использования. Этот пакет
написан заново и не включает сторонние skills или browser packages.

## 8. Сохранить, убрать из default, отложить

**Сохранить:** существующие проектные команды/CI, meaningful regression tests,
проверку работающего UI, честные ограничения, risk-based review, host permissions.
Governed-инструменты остаются доступны текущим пользователям.

**Убрать из Native:** обязательные brief/design approvals, CF-chain, назначение
всех ролей, четыре review на feature, task schemas, receipts на каждую команду,
review registry, prompt renderer, обязательные journals, отдельный critic,
скриншотные baseline для каждого изменения, обязательный MCP и model routing.

**Не строить:** собственный orchestrator, dashboard, memory service, agents SDK,
plugin marketplace backend, browser abstraction framework, autopilot с скрытыми
расходами, каталог из десятков внешних skills.

**Отложить до фактической нужды:** детерминированный installer/doctor, поддержка
других agents, автоматический update, дополнительные packs, rollout в downstream.
Добавлять механизм только после повторяемого failure, который он исправляет.

Найденные ранее дефекты Governed (`.agents/skills` не обнаруживается старым
security gate, clipping в context renderer, недостаточная browser identity)
сохранены в плане maintenance. Они не превращаются в prerequisite Native,
который эти инструменты не использует. Мы не объявляем старый gate покрывающим
новый пакет и не меняем его поведение исподтишка.

## 9. Что действительно требует решения владельца

1. **Права подписчиков на использование и изменение пакета.** Сейчас отсутствие
   root license намеренно закреплено в [LEGAL_STATUS](../LEGAL_STATUS.md).
   Нужна явно выбранная лицензия/разрешение хотя бы для распространяемого пакета.
   Документ не меняет эти права и не выбирает лицензию за владельца.
2. **После release checks — разрешение публичного выпуска.** Куда публиковать
   пакет и какой поддерживаемый канал объявлять в Telegram. До готового
   install artifact и результатов smoke это не запрос на approval вслепую.
