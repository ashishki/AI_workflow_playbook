# Playbook Native: продуктовая модель

Пересмотр 2026-09-19. Кандидат preview.6; публичного выпуска нет.
Работаем только в ветке `docs/codex-frontend-skills-mcp-20260919`.

**Playbook — небольшой пакет для работы внутри Codex.** Пользователь открывает
подготовленную папку и описывает задачу. Пакет задаёт границы работы и проверки,
добавляет независимое ревью через существующий Role Runner. Отдельного приложения,
чата или обязательного конструктора запросов нет.

Это проверяемая продуктовая гипотеза. Современный агент уже умеет планировать,
писать код, запускать проверки и пользоваться skills. Само повторение этих
инструкций не доказывает пользу Playbook. Критерий: меньше оставшихся дефектов
или ручного управления при приемлемых затратах на одинаковых задачах.

## Пользователь получает

- Один комплект: готовая папка «Мой проект», два skills, короткие инструкции,
  включённый reviewer и необязательная помощь `START.html`.
- Прямой путь: открыть папку в Codex → написать задачу → посмотреть и попробовать
  результат → продолжать в том же проекте. Формы и названия ролей знать не нужно.
- Для своего проекта — тот же пакет через штатное подключение, с сохранением
  существующих инструкций и локальных изменений.
- Понятный итог: что работает, как открыть, что действительно проверено,
  что пока не сделано или недоступно.

Доступ к Codex приобретается/предоставляется отдельно. Для независимого ревью
в среде агента нужны Python 3.10+ и авторизованный Codex CLI. Desktop-вход сам
по себе не подтверждает доступность CLI. На машине без этой возможности агент
выполняет доступные проверки и явно сообщает, что независимого ревью не было.
Поддержка Windows, macOS и Linux проверяется отдельно на уровне пакета и desktop.
Наш пакет пока не испытан с Claude Code; переносимость Markdown этого не заменяет.

## Один вход, три независимых выбора

| Измерение | Как определяется | Что пользователь может изменить |
|---|---|---|
| Новый / существующий проект | Файлы и задача; новая функция может быть в старом проекте | «Начни с нуля» / «Измени этот проект» |
| Создать / исправить / проверить | Желаемый результат, симптом или запрос на оценку | «Только найди проблемы, не исправляй» |
| Автоматически / сначала план / расширенный контроль | Автоматически по умолчанию, другое — по запросу | «Сначала план» / «Особенно проверь сохранность данных» |

Агент коротко объясняет подход и продолжает ясную работу. Быстрый режим убирает
лишние документы и вопросы, сохраняя проверку результата и автоматическое ревью.
План останавливается до записи файлов; check-only сохраняет исходники.
Расширенный контроль добавляет проверки по риску, а не согласование каждого шага.

`START.html` нужен только при затруднении: объясняет открытие папки, содержит
учебный пример, карточки сценариев и помощь. Конструктор запроса по умолчанию
свёрнут. Он не запускает Codex, не читает репозиторий и не отправляет задачи.
Основной вход и выбор режима находятся в разговоре с агентом.

## Что сохраняем в пакете и зачем

| Часть | Ответственность | Как проверяем её пользу |
|---|---|---|
| `playbook` | Границы задачи, переход к реальному пользовательскому результату, понятный итог | Результат, сохранность, plan/check boundaries; сравнение с plain agent |
| Короткий проектный блок | Указывает на установленный skill и ключевые ограничения | Discovery, отсутствие конфликтов и ненужного дублирования |
| `playbook-frontend` | Работающий экран: реализация, действия пользователя, вид, исправления | Внешний browser probe, просмотр свежих изображений, честность claims |
| Существующий Role Runner | Одно независимое ревью после изменения кода, включая quick | Найденные подтверждённые дефекты, ложные замечания, дополнительные затраты |
| Connection reference | Connect/update/remove с сохранением пользовательских файлов | Реальные lifecycle и негативные fixtures |

Skills короткие; reference читается по потребности. При наличии равноценного
проектного skill агент использует установленный процесс. Не ставим каталог
сторонних skills по умолчанию. Штатные возможности host не дублируем своим
orchestrator, памятью, task graph или маршрутизацией моделей.

Автоматический Role Runner сохраняется по явному решению автора. Его прежние
сравнения подтвердили конкретные изменения механизма и сокращение затрат
относительно старого Role Runner. Они **не доказывают**, что полный Native лучше
обычного Codex или что reviewer нужен на каждой возможной задаче. Эти вопросы
нуждаются в отдельном сравнении полного цикла. Reviewer не запускает reviewer;
тесты, браузер и исправления остаются ответственностью основного агента.

## Проверка результата без бюрократии

Агент проверяет то, что пользователь собирается делать. Для формы — заполнение,
отправку и наблюдаемый результат; для данных — сохранение, повтор, ошибки и защиту
исходника. Проходящий тест компонента не подтверждает весь сценарий. Учебная форма,
сохранённая заявка, реальная интеграция и опубликованный сервис — разные результаты.
Агент не додумывает бизнес-правила и прямо называет недостающие части.

Для frontend: прочитать существующий UI → реализовать → запустить текущий checkout
→ пройти основной сценарий и уместную ошибку → посмотреть свежие скриншоты узкого
и широкого экрана → исправить → повторить затронутые проверки. Доступные ошибки
console/network и клавиатура дополняют проверку. Нет браузера — нет утверждения
«UI проверен». Чужой сервер, старая сборка и старый screenshot не подходят.

Обычной задаче достаточно фактических checks и короткого итога. Полезная регрессия
остаётся в проектных тестах. Отдельные journals, receipts, JSON registries и ручная
подпись на каждом screenshot не нужны. Для работы на несколько сессий достаточно
существующего issue/плана с текущим состоянием и следующим шагом.

Человек решает неоднозначные продуктовые вопросы и внешние действия, на которые
ещё нет полномочий. Повторно спрашивать разрешение на уже порученную работу
не нужно. Host/repo permissions сохраняются; недоступность инструмента не лечится
отключением ограничений или скрытой публикацией локального приложения.

## MCP по потребности

Сначала используем доступный browser, CLI или проектный runner. MCP полезен,
когда даёт нужный доступ к браузеру, Figma, задачам, документации или диагностике
без ручного переноса контекста. Он не является обязательным слоем Playbook и не
становится зависимостью создаваемого приложения.

Не утверждаем, что CLI всегда быстрее MCP. Сравниваем конкретную интеграцию при
равном доступе и задачах. Новый аккаунт, установка, профиль браузера и внешние
изменения требуют соответствующих полномочий; уже подключённый инструмент можно
использовать в разрешённой области.

## Что исключено и что отложено

Из Native исключены обязательные brief/design approvals, CF-00–CF-09, назначения
ролей, четыре review на feature, prompt renderer, формальные реестры, обязательный
MCP, отдельный dashboard и собственный агентный runtime. START не является шлюзом
для каждой задачи. Новая обёртка без измеримой пользы не решает продуктовую проблему.

Governed сохранён для уже подключённых проектов и явного выбора. Его договорённости
не отменяются установкой Native. Старые defects discovery/context renderer/browser
identity относятся к отдельному maintenance; их не маскируем новым интерфейсом.
Не меняем замороженные пилоты и не запускаем автоматическую миграцию downstream.

Детерминированный installer, doctor, другие agents, автоматические обновления и
дополнительные packs добавляем только после наблюдаемой потребности. Новая
лаборатория не нужна: используем существующий Harness Lab, Ground Truth Lab отложен.

## Доказательства и следующий шаг

[История испытаний](../../reports/native/README.md) различает модель, механизм,
браузер и проход новичка. Ранее обычный Codex и Native оба исправили дефекты формы;
превосходство Native не установлено. Lifecycle/discovery CLI и один полный
agent/browser пример подтвердили реализуемость, но не массовое удобство desktop.

Новое [сравнение plain/current/lean](../../evals/native/VALUE_CHECK_RU.md) задаёт
общие задачи, данные, инструменты и бюджет заранее. Отдельно считаем качество,
завершение задачи и затраты; сохраняем таймауты. При ничьей польза не доказана.
Сравнение без reviewer оценивает только инструкции, не весь продукт.

[План реализации](CODEX_FRONTEND_IMPLEMENTATION_PLAN_RU.md) направлен сначала на
проверку полезной разницы и простого первого запуска, затем на выпуск.
[Протокол автора](../native/DEVELOPMENT_RU.md) — постоянный цикл улучшений.
Подписчику эти документы и лаборатория не устанавливаются.

От владельца нужны права использования распространяемого пакета и, после
готовности, решение о публикации. Остальные технические решения и проверки
исполнитель делает в согласованной области. [Legal status](../LEGAL_STATUS.md)
пока не даёт дополнительной лицензии; публичного выпуска нет.
