# Codex, frontend skills и MCP: предложение по развитию AI Workflow Playbook

Статус: **PROPOSED — исследование и проект внедрения, не утверждённая политика**.  
Дата исследования: 2026-09-19.  
Проверенная база: `ashishki/AI_workflow_playbook`, `master`, `d570163ab17ec3b4245187c778f1e8d89af9690f`.  
Область: преимущественно frontend; общие улучшения Playbook — только там, где они поддерживают эту работу.  
Реализация механизмов и установка skills/MCP в этой ветке **не выполняются**.

**Основное предложение:** сохранить Codex основной средой; добавить небольшой опциональный frontend pack, воспроизводимые браузерные проверки и проверяемое подключение инструментов. MCP не делать обязательной зависимостью ни Playbook, ни создаваемых продуктов.

Порядок реализации, ответственные, проверки и критерии принятия находятся в [плане внедрения](CODEX_FRONTEND_IMPLEMENTATION_PLAN_RU.md). Инструкции для следующей сессии — в [handoff](../handoffs/CODEX_FRONTEND_SKILLS_MCP_HANDOFF.md). Эти документы не заменяют `PLAYBOOK.md`, текущий task graph или утверждённый Feature Design.

## 1. Что именно исследовано и чего исследование не доказывает

Повторно проверена выдача mysetup: на дату исследования она содержит **15**, а не ранее упомянутые 14 сетапов [S01]. Для вопроса о frontend/skills/MCP подробно разобраны семь наиболее относящихся к нему опубликованных профилей [S02–S08], публичные инструкции конкретных skills и официальная документация инструментов. Это целевой разбор, а не аудит исполнения всех установок сообщества.

Различаются три уровня источников:

- **Описание автора:** человек сообщает, что инструмент установлен или используется. Это не trace конкретного запуска и не измерение эффекта.
- **Публичная реализация/документация:** можно установить, что skill предписывает и какие возможности предоставляет инструмент. Это ещё не проверка совместимости с конкретной установленной версией Codex.
- **Предложение для Playbook:** решение, которое предстоит проверить. Оно не становится обязательным от появления этого текста в Git.

Приватные `prp`, `verify`, browser-QA и другие командные skills авторов не были доступны как исходный код. Их нельзя считать проверенными пакетами, восстанавливать дословно или приписывать им неизвестные внутренние механизмы. Здесь заимствуются опубликованные принципы и предлагается собственная реализация.

## 2. Skill, инструмент, MCP, plugin и проверка — разные вещи

| Понятие | Практический смысл | Чего само по себе не обеспечивает |
|---|---|---|
| Skill | Повторно используемая инструкция: когда включаться, какие шаги выполнить, что прочитать и какой результат подготовить | Новую способность модели, права доступа, гарантированное выполнение инструкции |
| CLI/API-инструмент | Реально выполняет действие: запускает тест, открывает браузер, читает данные | Правильную постановку задачи и решение о приёмке |
| MCP | Стандарт связи между агентной средой и серверами инструментов/контекста | Обязательную архитектуру продукта, безопасность сервера, качество дизайна |
| Plugin | Упаковка возможностей; может объединять skills, подключение инструментов и настройки конкретной среды | Автоматическую переносимость всех hooks, команд и permissions между средами |
| Validator/test | Машинно проверяет сформулированное условие | Удобство продукта в целом или человеческое одобрение визуального решения |

Codex поддерживает skills с `SKILL.md`, дополнительными scripts/references и явным вызовом через `$`/`/skills`; возможно и включение по описанию задачи. Подробные инструкции загружаются по необходимости. Это удобно для небольших сценарных пакетов, но не превращает Markdown в принудительную защиту [O01].

В схеме MCP агентная среда является host, соединение обслуживает client, а server предоставляет доступные возможности. Сервер может быть локальным процессом или удалённым сервисом. Наличие MCP у инструмента разработки не означает, что библиотеку MCP нужно добавлять в backend приложения [M01].

**Ответ на вопрос «все мои проекты без MCP — это недостаток?» — нет.** Недостатком может быть отсутствие доступа к необходимому контексту или отсутствие проверки работающего интерфейса. MCP — один из способов дать такой доступ. Скрипты, CLI и прямые API тоже могут решать эту задачу.

## 4. Конкретные frontend skills: назначение, переносимость и ограничения

### 4.1. `frontend-design`: сначала направление, затем код

Публичный skill в официальном Anthropic plugin pack предлагает привязать визуальные решения к предмету и аудитории, подготовить краткое направление и систему визуальных параметров, сопоставить их с brief, затем реализовать и критически осмотреть результат [P01].

Это текстовая методика, не недоступная Codex технология. Её смысл можно перенести в собственный frontend skill после проверки лицензии и зависимостей. Однако plugin целиком, его hooks и команды не следует считать переносимыми без адаптации.

**Предлагаемая адаптация:** продуктовая задача, реальные тексты, существующие компоненты, контраст, читаемость, состояния и поведение важнее декоративной необычности. Рабочий кабинет терапевта не должен становиться рекламным лендингом. Изменять сложившуюся дизайн-систему только по согласованной задаче.

Официальные frontend-инструкции OpenAI также различают рабочие приложения и выразительные промостраницы и предлагают учитывать существующие соглашения [O03]. Их страница указывает целевую модель GPT-5.5: это источник принципов, а не доказательство превосходства или готовый обязательный prompt для текущей модели пользователя.

### 4.2. `vercel-react-best-practices`: инженерная часть React/Next.js

Публичный skill направляет работу с загрузкой данных, размером bundle, серверными/клиентскими границами и лишними перерендерами. Он отсылает к отдельным правилам и примерам [P02].

**Применять:** когда проект действительно использует совместимую версию React/Next.js и задача касается соответствующей области. Выбирать релевантные правила, а не загружать весь сборник каждый раз. Рекомендация оптимизации должна иметь измеряемую причину или понятный предотвращаемый дефект.

**Не применять:** ко всем проектам на Python, статическому HTML или другому framework автоматически. Наличие этого skill не является причиной переписывать frontend на Next.js, добавлять библиотеку или преждевременно усложнять компонент.

### 4.3. `vercel-composition-patterns`: устойчивые компоненты

Skill посвящён композиции компонентов, разрастанию boolean props, распределению состояния и API компонентов. Некоторые указания явно зависят от React 19 [P03].

**Применять:** к повторно используемым элементам и действительно сложным вариантам поведения. Проверять версии в lockfile. Не переделывать небольшую локальную форму в архитектурный framework ради соответствия всем паттернам.

### 4.4. `web-design-guidelines`: проверка, а не генератор красоты

Публичный `SKILL.md` предписывает получить актуальные правила из другого репозитория, проверить выбранные файлы и вернуть замечания с привязкой к строкам [P04]. Следовательно, фиксация версии только самого skill не фиксирует содержимое правил: ссылка на `main` остаётся изменяемой.

**Предлагаемая адаптация:** сохранить проверенную версию внешнего набора правил или его immutable reference и hash; записывать использованную редакцию в evidence. Отдельно разрешать обновление. Сопоставить вызов `WebFetch` с фактически доступным инструментом Codex, а не считать имена инструментов универсальными.

Этот review даёт статические замечания. Проверка DOM, реального взаимодействия, клавиатуры и скриншотов остаётся отдельной.

### 4.5. Superpowers и личные workflow skills

Superpowers публично описывает поддержку Codex и сценарии планирования, test-first и проверки результата [P05]. Поэтому привязка такой методики только к Claude неверна.

Но в Playbook уже есть собственные планирование, review policy, bounded correction и human gates. Установка второй полной методологии может создать конфликт источников истины. Предлагается не включать Superpowers целиком по умолчанию: брать проверяемые узкие приёмы и сопоставлять их с существующими механизмами.

`web-perf`, `handoff` и другие названия без достаточной ссылки на реализацию не включаются в список одобренных пакетов. Сначала установить источник, содержимое, лицензию, зависимости и поведение.

## 5. Можно ли реализовать всё это только Codex

**Да — как процесс разработки без обязательного Claude.** Это не обещание идентичных результатов разных моделей. Качество нужно измерить на реальных задачах пользователя.

Предлагаемая последовательность:

```text
Человек: задача, аудитория, ограничения, референс и решение о приёмке
  → основная сессия Codex: план и управление утверждённым слайсом
  → Codex implementer: код, тесты, запуск приложения и сбор evidence
  → детерминированные проверки проекта и браузерного поведения
  → свежий независимый Codex reviewer: код, критерии и evidence
  → человек: визуальная приёмка и решение о merge/release
```

«Только Codex» не означает «один бесконечный чат, проверяющий сам себя». Одна модель может использоваться в разных процессах, но независимость проверяющего контекста и независимость тестовых критериев надо организовать. Межвендорность не является обязательным условием и не гарантирует независимость ошибок.

Существующий Role Runner поддерживает только `product_design_review`, `program_design_review`, `slice_review`, `maintainability_review` [R02]. Визуальный/UX checklist сначала передавать как дополнительную область существующего `slice_review`. Не вызывать выдуманную поддерживаемую роль `frontend_critic`. Для других ролей использовать только уже разрешённый проектом механизм отдельных сессий.

Сохранять текущие настройки основной модели пользователя. Перед экспериментом зафиксировать фактические model/effort/CLI version и review policy; не подменять их названиями моделей из чужих профилей. При недоступности требуемого reviewer-профиля получить явное решение, а не незаметно снижать режим.

### Что даёт фронтенду качество

Для proposed frontend pack важнее не количество skills, а полный цикл: конкретный brief; существующая дизайн-система или согласованный визуальный ориентир; основные и ошибочные состояния; исполнимые сценарии; просмотр реального приложения; исправления в пределах бюджета; независимая проверка; человеческая приёмка.

Веб-frontend, Telegram Mini App и чистый Telegram-бот — разные поверхности. Для чистого бота проверяются сообщения, клавиатуры, восстановление и изменения состояния; не нужно искусственно добавлять веб-интерфейс ради Playwright. Для Mini App потребуется отдельная проверка особенностей целевого Telegram WebView, а не только обычного desktop Chrome.

## 6. Когда MCP действительно полезен

### 6.1. Базовый вариант без MCP

Codex использует shell и существующие команды проекта. Playwright Test хранит повторяемые e2e/visual tests в репозитории. Для исследования страницы допустим Playwright CLI или доступный в конкретной среде встроенный браузер. Возможности среды проверяются явно, а не предполагаются по наличию подписки.

Playwright CLI и Playwright Test — не одно и то же: первый удобен для интерактивных действий агента, второй — для воспроизводимых тестов. Исследованный CLI поддерживает браузерные сессии и скриншоты. Авторы Playwright MCP отдельно предлагают CLI+skills для coding agents; это рекомендация авторов, а экономию в данном проекте предстоит измерить [B01, B02].

Таким образом, путь «Codex → CLI/тест → браузер → evidence» вполне полноценен. Критично наличие проверяемого результата, а не транспорт вызова.

### 6.2. Выбор подключений по конкретной задаче

| Потребность | Предлагаемый первый выбор | Когда добавлять MCP | Ограничение |
|---|---|---|---|
| Повторяемая проверка пользовательского сценария | Существующий test runner + Playwright Test | Не обязателен | Сценарии должны сохраняться и запускаться без свободного рассуждения модели |
| Интерактивное исследование DOM и UI | Playwright CLI или проверенный встроенный browser | Playwright MCP, если нужен именно этот tool interface | Не устанавливать одновременно несколько браузерных серверов без необходимости |
| Network/console/performance debugging | Доступные средства браузера | Chrome DevTools MCP при реальной потребности | Отдельный тестовый профиль; проверить передачу telemetry и trace URL |
| Перенос конкретного Figma-макета | Предоставленный экспорт + компоненты проекта | Figma MCP, если макет и design tokens действительно живут в Figma | Начать с чтения конкретных frames; не давать запись на canvas автоматически |
| Документация framework | Версия проекта + официальные документы | Docs MCP при повторяющейся измеримой проблеме поиска | Не подключать «на всякий случай» и не считать любой возвращённый текст актуальным |
| GitHub, тикеты, сообщения | Git/существующие API/CLI | MCP только при удобстве и доступных ограничениях | Не дублировать уже достаточный интерфейс |

Chrome DevTools MCP предоставляет browser debugging и performance-инструменты; в документации также указан CLI-путь. Документация предупреждает об экспонировании данных браузера, включённой telemetry и возможной отправке URL для CrUX. Предлагаемые безопасные настройки должны учитывать эти отдельные каналы, а не только режим incognito [B03].

### 6.3. Пример применения Figma MCP

Человек даёт ссылку на конкретный frame. Агент получает структуру и контекст дизайна через доступные read-tools, при необходимости screenshot и переменные; сопоставляет элементы с существующими компонентами; пишет код; запускает приложение; сравнивает фактический UI с согласованным ориентиром. Фактические названия tools и permissions проверяются при подключении [F01, F02].

Figma screenshot доказывает вид макета, а не вид реализации. HTML/CSS из design-context не является обязательной архитектурой проекта. Текущий Figma MCP имеет также write-возможности: их исключить из стартового allowlist, а не считать весь сервер read-only.

Когда Figma-макета нет, MCP не нужен для того, чтобы Codex придумал и реализовал интерфейс. Достаточны согласованный brief, референсы, собственные компоненты и полноценная проверка.

### 6.4. Как вводить любое MCP-подключение

Сначала определить недостающую возможность и сравнить с CLI. Затем проверить publisher, source/version либо remote endpoint identity, лицензию, transport, данные, полномочия и стоимость. Для локального сервера зафиксировать пакет и зависимости; для непиннуемого remote server сохранить наблюдаемые metadata/tool schemas и проверять drift, не обещая immutable server code.

В Codex конфигурации подключений используются `config.toml`, команды `codex mcp` и `/mcp`; доступны allow/deny lists инструментов и timeout-настройки. Конкретные поддерживаемые поля и scope конфигурации сверять с установленной версией [O02].

До реальной работы необходим smoke test на синтетических данных: правильный ресурс, ожидаемый результат, запрещённое действие, отсутствие сервера, timeout, истёкший доступ. Обязательная проверка при недоступном инструменте получает BLOCKED, а не PASS. Отключение соединения и отзыв доступа должны быть понятны человеку.

## 7. Что уже существует в Playbook и какая нужна дельта

### Критичный первый пробел: видимость skills для security gate

Официальная документация Codex описывает `.agents/skills`, включая repo/user locations и symlinked folders [O01]. Проверяемый gate Playbook не включает repo `.agents/skills` в default discovery [R04]. Следовательно, простая установка туда нового pack может оказаться вне этой конкретной проверки. Это не утверждение об отсутствии всех остальных защит.

В этой сессии выполнена **изолированная репродукция алгоритма обхода**: fixture только в `.agents/skills` дал пустой список; после добавления fixture в `.codex/skills` был найден только legacy fixture. Использован извлечённый алгоритм, а не полный CLI security gate. Scanner, installed Codex и полный repository pytest здесь не запускались. Это подтверждение узкого поведения, не аудит всей цепочки доверия.

Будущий discovery должен учитывать объявленные effective roots, nested repository scopes и разрешённые symlinks. Глобальные/home/admin/plugin skills не надо автоматически копировать в Git или сканировать за пределами разрешённой области: их присутствие и coverage должны быть явно известны. Неизвестное покрытие нельзя выдавать за полную проверку.

## 8. Предлагаемый минимальный frontend pack

Это **предлагаемые имена**, не команды или файлы, уже существующие в Playbook.

| Skill | Вход | Что делает | Выход / граница |
|---|---|---|---|
| `playbook-frontend-design` | Текущая задача, brief, framework/version, components, visual route | Формирует UX-сценарии и компактное визуальное направление, проверяет совместимость с существующим продуктом | Раздел утверждаемого Feature Design; сам ничего не утверждает и не меняет код на стадии design |
| `playbook-frontend-verify` | Task/slice, AC, build identity, тестовая среда | Вызывает существующие project checks, собирает browser evidence, перечисляет пробелы | Кандидат evidence; не превращает `DONE` в приёмку и не меняет baselines без разрешения |
| `playbook-frontend-review` | Diff, критерии, проверенные evidence references | Направляет отдельный reviewer на behavior, layout, a11y, content, maintainability | Findings через существующий reviewer protocol; implementer не использует его как независимое саморевью |

`vercel-react-best-practices` и `vercel-composition-patterns` — условные справочные пакеты только для подходящего стека. `web-design-guidelines` — источник закреплённых правил для review. Отдельные skills `resume`, `ship-it`, `preflight` сначала не создавать, если то же уже доступно через feature workflow и tools.

До реализации pack остаётся в документации. Внедрять его как opt-in companion/template, а не включать автоматически для всех backend-репозиториев. Конкретную папку шаблонов и installer flag утвердить в Feature Design. Изменение глобального пользовательского Codex config требует отдельного разрешения.

В каждом skill должны быть узкий trigger, перечисление обязательных входов, отказ от догадок об authority, выбор scoped references, допустимые tools и остановки. Содержимое policy не копируется целиком: skill направляет к проверяемым источникам. Для операций с последствиями предпочтителен явный вызов и исполнительные ограничения; только текстового запрета недостаточно.

## 9. Качество frontend: что и кто проверяет

| Слой | Метод | Кто исполняет / кто оценивает |
|---|---|---|
| Соответствие задаче | Наблюдаемые сценарии и критерии до реализации | Человек утверждает; Codex готовит |
| Код | Typecheck/lint/unit/component tests и проверки stack conventions | Детерминированный runner; независимый code/slice reviewer |
| Пользовательское поведение | E2E с assertions, негативные состояния, сохранение/повтор/восстановление | QA-driver или implementer собирает; независимый reviewer перепроверяет доказательства |
| Внешний вид | Stable screenshots, baseline/current/diff, coverage по состояниям | Runner собирает; человек принимает новый/изменённый обязательный baseline |
| Доступность | Автоматические проверки плюс клавиатура, focus, zoom и семантика по AC | Runner и reviewer; человек проверяет критичный сценарий |
| Производительность | Повторяемые измерения при одинаковой среде и заранее выбранные бюджеты | Runner; reviewer объясняет regression, человек принимает trade-off |
| Реальное удобство | Выполнение задачи целевым пользователем без подсказок разработчика | Пользователь; владелец фиксирует наблюдения и решение |

Playwright visual assertions зависят от стабильности окружения; обновлённый baseline не может сам доказать корректность изменения [B04]. Автоматическая accessibility-проверка находит лишь часть проблем, поэтому она не заменяет ручные проверки [B05]. Действующий UI protocol Playbook уже требует разграничивать такие доказательства [R03].

Не использовать универсальный балл «дизайн 9/10» как release gate. Визуальный critic может предложить наблюдения, но не может подтвердить способность человека выполнить задачу. Отсутствие screenshot/браузера/vision capability у reviewer нужно указать как непроверенную область.

## 10. Порядок внедрения и критерий успеха

Сначала утвердить одну небольшую реальную frontend-задачу и baseline. Затем исправить skill discovery, защитить обязательный контекст и привязать browser evidence к правильной сборке. После этого добавить opt-in skills и проверить Codex-only цикл **без MCP**. Только при подтверждённой необходимости сравнить вариант с одним browser MCP. Figma оценивать отдельно, когда существует реальный макет.

Полный backlog CF-00–CF-09, зависимости, роли и отрицательные тесты описаны в [плане](CODEX_FRONTEND_IMPLEMENTATION_PLAN_RU.md). Успех — меньше ручной реконструкции состояния, меньше повторных исправлений и достоверная приёмка; не число установленных расширений и не количество сгенерированных строк.

Результат сравнения может быть `adopt`, `adopt_limited`, `inconclusive` или `reject`. Это proposed labels для решения владельца, не новые статусы существующих validators. Нулевой MCP-набор остаётся допустимым итогом.
