# Как развивать Playbook и проверять улучшения

Это рабочий протокол автора продукта. Подписчику его читать не нужно.
Для испытаний используем существующий
[Harness Lab](../../companion/ai_workflow_harness_lab/README.md).
Eval Ground Truth Lab откладываем: подключение второй лаборатории сейчас не требуется.

## Что мы делаем

Playbook — небольшой пакет инструкций и skills для Codex. Пользователь открывает
проект, описывает задачу, получает реализацию, проверку результата и понятный итог.
`START.html` — инструкция и необязательный помощник составления запроса.
Работа с файлами происходит в Codex. Автоматическое независимое ревью выполняет включённый Role Runner.
Собственный чат и обязательный MCP в продукт не входят. Лаборатория и инструменты сборки остаются у автора.

## Один цикл улучшения

1. **Назвать проблему.** Например: «новичок открыл START и ждёт, что агент
   начнёт работу прямо там». Достаточно абзаца в задаче или чате.
2. **Выбрать одно изменение и критерий.** Например: явно объяснить переход
   в Codex; человек без подсказки открывает нужную папку и отправляет задачу.
   Заранее назвать сравниваемые версии, условия, число попыток и предел затрат.
3. **Сделать минимальную правку.** Не добавлять новый режим, роль или документ,
   если проблему решает более ясный текст или имеющаяся возможность агента.
4. **Проверить механизм и результат.** Сначала дешёвые проверки затронутого
   участка, затем подходящие реальные задачи. Сохранить и неудачные попытки.
5. **Принять решение.** Оставить, доработать или откатить. Зафиксировать коротко:
   проблема → изменение → наблюдение → ограничение → решение. Собрать новую
   версию комплекта, если менялись доставляемые файлы.

Отдельные ADR, feature design, граф задач и обязательные review-роли для каждого
такого цикла не нужны. Существующий Governed-процесс применяется только там,
где его явно выбрали; он не включается автоматически из-за наличия в репозитории.

## Как выбирать проверку

| Что меняем | Как проверяем | Что считается достаточным результатом |
|---|---|---|
| Текст первого запуска | Открываем комплект на поддержанной системе; затем наблюдаем новичка | Человек сам доходит до задачи и открывает результат |
| Entry skill / выбор процесса | Парные задачи в Harness Lab, чтение итогов и изменений | Задача выполнена; «план» и «проверить» сохраняют свои границы |
| Frontend skill / browser channel | Работающий UI, действия пользователя, мобильный и широкий экраны, просмотр скриншотов | Исправлена реальная проблема; агент честно описал собственные проверки |
| Подключение / обновление / удаление | Чистое временное окружение, повторное подключение, сохранность пользовательских файлов | Skills доступны в новой сессии; удаление сохраняет работу пользователя |
| Новая модель, MCP или сторонний skill | Та же задача и инструменты; меняется один выбранный фактор | Польза видна на оговорённых случаях и оправдывает сложность/затраты |
| Сборка ZIP | Тесты сборщика, извлечение, хеши, браузерная проверка именно извлечённой страницы | Получатель получает проверенные файлы, а прежняя версия не перезаписана |

Быстрый режим убирает промежуточные документы, а не проверку результата.
Проходящий тест сам по себе не доказывает качество: сначала убеждаемся, что
проверка ловит исходную ошибку или специально внесённый дефект.

## Harness Lab — единое место сравнений

[Native suite и команды](../../evals/native/harness/README.md) используют готовые
`run`, `verify-bundle`, `compare` лаборатории. Тонкий адаптер только подключает
skills в одноразовую копию и запускает Codex. Форматы доказательств, таймауты и
сравнение принадлежат Harness Lab; ещё один runner не создаём.

Сейчас suite проверяет **backend-исправление, plan-only, review-only и frontend**.
Новый проект и lifecycle дополнительно проверяются существующими probes.
Это ограниченное покрытие, не оценка всех 18 сочетаний процесса. Добавляем случаи
по наблюдаемым рискам, а не ради заполнения матрицы. Старый `evals/native/run.py`
остаётся для воспроизведения диагностик; новые сравнения развиваем в Harness Lab.

Обычная база — предыдущая версия Playbook. Периодически сравниваем с обычным
Codex, чтобы не сохранять механизмы без пользы. Между условиями сохраняем задачу,
fixture, модель, effort, разрешения, доступные инструменты, дедлайн и общие
инструкции. Пакеты и suite фиксируем по Git SHA/хешам. Идентичность модели в Lab
заявляется оператором: проверяем её по фактической сессии, не угадываем.

Начинаем с одного диагностического прогона на условие. Для решения об изменении —
как минимум две попытки на условие в затронутых задачах, с чередованием порядка.
Это нижний порог для локального решения, не статистическое доказательство пользы.
Не выдаём случай, на котором подбирали текст, за независимую проверку: добавляем
свежий пример. Более сильное публичное обещание требует более сильного испытания.

Реальные CLI-прогоны выполняем в отдельных процессах на копиях fixtures.
По явному запросу автора агент может запускать такой worker из рабочей сессии;
он не использует реальный downstream-проект. Участник эксперимента не запускает
новый эксперимент рекурсивно. Role Runner запускает одну независимую сессию
ревью, а ревьюер не создаёт новых ревьюеров. Ограничения разрешений сохраняются.
Тесты с fake CLI проверяют только работу адаптера и оценщиков.

## Как читать итог

- **Успех задачи:** внешний критерий выполнен, границы соблюдены, итог честный.
- **Ошибка задачи:** выполнение завершилось, но результат или границы неверны.
- **Невалидный запуск:** отказ инструмента, неполный/повреждённый trace, таймаут
  исполнения. Показываем отдельно; повтор не стирает исходную неудачу.
- **Не измерено:** понятность новичку, неизвестная цена, недоступный браузер
  или другая непроверенная характеристика.

`exit 0`, целостный bundle и зелёный `compare` не равны готовности продукта.
Смотрим оценки каждой задачи и регрессии. Текущий Native adapter не превращает
свободный текст ответа в структурированные claims: метрика `false_success_rate`
из общего отчёта Lab здесь не доказывает честность ответа. Её проверяем чтением
итога и trace. В плане автоматически проверяется сохранность файлов; полезность
самого плана оценивает человек. Неизвестную стоимость не объявляем нулевой. В Native сравнение суммирует токены
основного агента и выполненных Role Runner ревью; отсутствие счётчика оставляет
полный итог `unknown`, а не заниженную частичную сумму. Время основного запуска
уже включает ожидание ревью и не складывается с ним повторно.

## Что хранить и когда выпускать

В Git остаются код, повторяемые случаи, инструкция и короткий отчёт с решением.
Raw traces, скриншоты и сборки по умолчанию — в ignored `.playbook-artifacts/`.
Для воспроизводимого внешнего заявления сохраняем полный пакет в доступном
архиве и даём неизменяемую ссылку; локального пути недостаточно.
[История Native](../../reports/native/README.md) сохраняет прежние доказательства
по фиксированному коммиту. Не исправляем замороженный манифест задним числом.

Агент сам исследует, реализует, проверяет и исправляет. Автор решает, какую пользу
обещаем, кому и на каких правах распространяем продукт. Новый публичный выпуск
опирается на фактический первый запуск в поддержанной среде и небольшой
[пилот с новичками](PILOT_RU.md). До этого статус — preview.

## Запрос для следующей сессии

```text
Развиваем Playbook Native по docs/native/DEVELOPMENT_RU.md.
Проблема пользователя: …
Проверь текущее состояние и предложи минимальное улучшение.
Используй существующий Harness Lab. Сначала назови критерий и условия сравнения,
затем внеси изменение и выполни доступные проверки. Реальные model trials
запускай отдельным worker на копиях fixtures в оговорённом бюджете;
результаты имитации не считай испытанием модели.
Покажи решение, доказательства, ограничения и следующий полезный шаг.
Не меняй master, downstream, глобальную модель и разрешения.
```
